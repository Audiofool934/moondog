# Spotify refresh transactions

Spotify refresh holds the credential store's process-shared filesystem lock through the OAuth exchange and the atomic credential commit. Each transaction re-reads the current credential under that lock. Reactive callers may reuse a different usable access token; changed metadata alone cannot satisfy a rejected-token refresh. Spotify API writes still dispatch once and are never replayed automatically.

A refresh that fails, times out, or dies with its process leaves the stored credential unchanged, and the next request tries the same refresh token again. A laptop that wakes before its network is back, a Spotify outage, or a rate limit therefore costs one failed request, not the sign-in. If Spotify did rotate the refresh token before the response was lost, Spotify answers the retry with `invalid_grant`; only that answer reports `spotify_refresh_rejected` and asks the listener to run `/spotify login`. Versions up to 0.2.1 fenced the credential with a durable `refreshAttempt` marker after any such failure and required a new login; a stored marker is now read and ignored, and the next successful refresh removes it.

After the initial credential read, the refresh deadline is 15 seconds, including lock wait. A cancelled caller stops waiting immediately. Once the exchange is dispatched, the bounded transaction continues to persist a rotated token even if every caller stops waiting; cancellation before dispatch starts no exchange. A late response after the deadline cannot write credentials. Disk operations finish before releasing the lock; a stalled filesystem can delay internal cleanup beyond the caller deadline.

Lock owners have unique filenames. Only the successful remover of a confirmed dead owner's exact file may remove the lock directory. Empty, malformed, or legacy fixed-filename locks are treated as busy, never stolen; the wait is bounded. An orphaned such lock requires manual local recovery after confirming no process owns it. Credential directories remain 0700 and files 0600. Custom credential stores without a coordinated `modify` transaction cannot refresh.

Tests use fictional credentials, injected token responses, independent Node processes, process termination, and persistence failures. No live OAuth exchange or grants are part of verification.
